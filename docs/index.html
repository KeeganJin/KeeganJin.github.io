Agent 架构模式

Agent 架构概述

Agent 架构定义了 Agent 系统各组件的组织方式和交互模式。选择合适的架构是构建有效 Agent 系统的关键。

单 Agent 架构

单 Agent 架构是最基本的 Agent 组织形式，一个独立的 Agent 完成所有任务。

基本结构

工作流程

  1. 接收输入：Agent 接收用户请求
  2. 理解意图：LLM 解析用户意图
  3. 规划行动：制定行动计划
  4. 执行行动：调用工具或生成内容
  5. 反馈整合：整合执行结果
  6. 输出响应：向用户返回结果

适用场景

单 Agent 架构适用于：

  • 相对简单的任务
  • 不需要协作的独立任务
  • 用户个人助手
  • 信息问答类应用

优势与局限

优势 局限
结构简单，易于实现 复杂任务处理能力有限
调试和维护方便 单点故障风险
响应延迟低 无法并行处理
成本可控 知识和能力有限

多 Agent 架构

多 Agent 架构使用多个 Agent 协作完成复杂任务。

基本结构

协作模式

对话协作模式

Agent 之间通过对话交流：

  • Agent A 发送消息给 Agent B
  • Agent B 处理并回复
  • 消息传递直到任务完成

代表框架：AutoGen 的 GroupChat

顺序协作模式

Agent 按顺序处理任务：

  • Agent A 处理第一步
  • Agent B 处理第二步（使用 A 的输出）
  • Agent C 处理第三步（使用 B 的输出）

代表框架：CrewAI 的 Sequential 流程

并行协作模式

多个 Agent 同时处理不同子任务：

  • Agent A 处理子任务 1
  • Agent B 处理子任务 2
  • 结果聚合后返回

适用场景：独立子任务可并行处理

适用场景

多 Agent 架构适用于：

  • 复杂的多步骤任务
  • 需要不同专业能力的任务
  • 需要并行处理的大任务
  • 需要多方视角的任务（如辩论、评审）

优势与局限

优势 局限
处理复杂任务能力强 结构复杂，实现难度高
专业化分工 Agent 间协调开销
可并行处理 成本较高
故障隔离 调试困难

层次化 Agent 架构

层次化架构使用层级组织 Agent，上层 Agent 管理下层 Agent。

基本结构

工作机制

Manager Agent

  • 接收用户任务
  • 分解任务为子任务
  • 分配子任务给 Worker
  • 收集 Worker 结果
  • 整合结果并返回

Worker Agent

  • 接收 Manager 分配的子任务
  • 执行具体任务
  • 可调用工具或下层 Worker
  • 向 Manager 上报结果

适用场景

层次化架构适用于：

  • 大型复杂任务（如软件开发、研究报告）
  • 需要多层分解的任务
  • 需要集中管理的场景
  • 企业级应用

优势与局限

优势 展现
任务分解清晰 层级管理开销
可处理超大任务 信息传递延迟
专业化分工明确 层级过深效率下降
易于扩展 Manager 成为瓶颈风险

代表框架：CrewAI 的 Hierarchical 流程、AutoGen 的层次化对话

黑板架构模式

黑板架构是一种协作模式，多个 Agent 共享一个”黑板”来交换信息。

基本结构

工作机制

  1. 黑板：共享的数据存储区域

    • 存储任务状态
    • 存储中间结果
    • 存储共享知识

  2. Agent：多个独立 Agent

    • 从黑板读取信息
    • 处理自己的部分
    • 向黑板写入结果

  3. 控制器：可选的控制组件

    • 决定哪个 Agent 活跃
    • 判断任务完成状态

适用场景

黑板架构适用于：

  • 多 Agent 协作但不需要直接对话
  • 信息共享需求强的任务
  • 异步协作场景
  • 专家系统集成

优势与局限

优势 局限
Agent 独立性强 黑板一致性管理复杂
信息共享方便 可能产生冲突写入
异步协作支持 读写顺序管理

消息传递架构

消息传递架构通过消息队列实现 Agent 间通信。

基本结构

工作机制

  1. 消息格式：标准化消息格式

  2. 消息队列：消息存储和传递

    • 消息持久化
    • 消息排序
    • 消息路由

  3. Agent 通信：

    • 发送消息到队列
    • 从队列接收消息
    • 处理消息并回复

适用场景

消息传递架构适用于：

  • 分布式 Agent 系统
  • 异步任务处理
  • 需要可靠传递的系统
  • 大规模 Agent 网络

优势与局限

优势 局限
解耦 Agent 消息延迟
可扩展性好 消息顺序管理复杂
支持异步 需要消息队列基础设施
容错能力强 消息丢失风险

混合架构

实际系统往往采用混合架构，结合多种模式的优点。

混合架构示例

混合策略

  1. 层次 + 黑板：Manager 通过黑板管理 Worker
  2. 层次 + 消息队列：层次间用消息队列传递
  3. 对话 + 黑板：Agent 对话同时共享黑板
  4. 并行 + 顺序：部分并行、部分顺序

架构选择考量

任务复杂度

任务复杂度 推荐架构
简单单步任务 单 Agent
中等多步任务 单 Agent + 工具
复杂多步任务 多 Agent（顺序）
超大复杂任务 层次化 Agent
多维度并行任务 多 Agent（并行）

团队规模

Agent 数量 推荐架构
1-2 单 Agent 或简单多 Agent
3-10 对话协作或层次化
10+ 层次化或消息传递

响应要求

响应要求 推荐架构
实时响应 单 Agent
秒级响应 简单多 Agent
分钟级响应 层次化或黑板
异步任务 消息传递

成本考量

成本敏感度 推荐架构
高度敏感 单 Agent，控制调用次数
中等敏感 多 Agent，优化协作流程
不敏感 复杂架构，追求最优效果

架构演进建议

从简单开始

建议架构演进路径：

  1. 第一阶段：单 Agent + 基础工具

    • 实现基本功能
    • 收集用户反馈
    • 了解任务复杂度

  2. 第二阶段：单 Agent + 多工具

    • 添加更多工具
    • 优化规划能力
    • 增强记忆系统

  3. 第三阶段：简单多 Agent

    • 针对复杂任务添加 Agent
    • 实现基本协作
    • 测试协作效果

  4. 第四阶段：复杂架构

    • 根据需求选择层次化/黑板/消息传递
    • 优化协作效率
    • 添加监控和调试能力

避免过度设计

常见错误：一开始就设计复杂的多 Agent 架构。

正确做法：根据实际需求逐步演进架构复杂度。

总结

Agent 架构选择需要根据任务复杂度、团队规模、响应要求、成本考量等因素综合判断。从单 Agent 开始，根据实际需求逐步演进，避免过度设计。

主流架构包括：单 Agent、多 Agent（对话/顺序/并行）、层次化 Agent、黑板架构、消息传递架构。实际系统往往采用混合架构。

LLM 与 Agent 的关系

LLM：Agent 的”大脑”

大语言模型（LLM）在 Agent 系统中扮演着”大脑”的角色。它负责理解输入、推理决策、生成输出——这些是 Agent 智能行为的核心来源。

LLM 在 Agent 中的角色

LLM 在 Agent 系统中承担多个关键职能：

1. 语言理解

LLM 的首要任务是理解用户的自然语言输入：

  • 意图识别：理解用户想要做什么
  • 任务解析：将模糊需求转化为明确任务
  • 上下文理解：基于历史对话理解当前请求
  • 歧义消解：处理不明确或多种解释的输入

2. 推理与规划

LLM 的推理能力是 Agent 决策的核心：

  • 任务分解：将复杂任务拆解为子任务
  • 步骤规划：确定完成任务所需的步骤顺序
  • 条件推理：根据条件选择不同的行动路径
  • 因果推理：预测行动的可能后果

3. 决策生成

LLM 根据推理结果生成具体决策：

  • 工具选择：决定调用哪些工具
  • 参数生成：生成工具调用的参数
  • 策略调整：根据执行反馈调整策略
  • 失败处理：处理执行失败的情况

4. 内容生成

LLM 生成 Agent 的输出内容：

  • 回答生成：生成对用户的回复
  • 报告撰写：生成分析报告、总结等
  • 代码生成：生成代码片段或完整程序
  • 解释说明：解释决策过程和结果

LLM 的能力边界

尽管 LLM 能力强大，但它也存在明确的局限。理解这些局限是设计 Agent 系统的关键。

LLM 能做什么

能力 描述
自然语言理解 高质量地理解文本语义、意图、上下文
知识问答 利用训练知识回答各类问题
内容生成 生成文本、代码、创意内容
推理能力 进行一定程度的逻辑推理和任务规划
多语言处理 处理多种语言的输入和输出
格式遵循 按指定格式生成输出（JSON、表格等）

LLM 不能做什么

局限 描述
实时信息获取 无法获取训练后的新信息
数学精确计算 复杂数学计算可能出错
长期状态维护 无法自身维护长期记忆
物理世界交互 无法直接操作物理世界
事实性保证 可能生成不真实的内容
无限上下文 上下文窗口有限
确定性执行 相同输入可能产生不同输出

从 Chatbot 到 Agent 的演进

Chatbot 的局限

传统的 Chatbot 系统存在明显局限：

  1. 单轮问答：每次输入独立处理，缺乏行动连续性
  2. 被动响应：只能回答问题，不能主动解决问题
  3. 无工具能力：无法获取实时信息或执行操作
  4. 短记忆：对话上下文有限，无法长期记忆

Agent 的突破

Agent 通过以下机制突破了 Chatbot 的局限：

1. 工具调用（Tool Use）

Agent 可以调用外部工具来扩展能力：

  • 搜索引擎：获取实时信息
  • 代码执行：进行精确计算
  • API 调用：与外部系统交互
  • 文件操作：持久化存储信息

2. 记忆系统（Memory）

Agent 维护多层记忆：

  • 短期记忆：当前对话上下文
  • 工作记忆：当前任务状态
  • 期记忆：跨会话的知识和经验

3. 规划能力（Planning）

Agent 可以规划多步骤行动：

  • 任务分解：复杂任务拆解为简单子任务
  • 步骤排序：确定行动顺序
  • 反馈调整：根据结果调整计划

4. 自主行动（Autonomy）

Agent 可以自主决策和行动：

  • 自主选择工具
  • 自主调整策略
  • 自主判断完成状态

LLM Agent 的典型架构

基本架构

详细架构

一个完整的 LLM Agent 通常包含以下模块：

输入处理模块

  • 接收用户输入
  • 解析意图和任务
  • 加载相关上下文和记忆

LLM 核心模块

  • 处理输入并生成决策
  • 进行推理和规划
  • 生成工具调用指令或输出内容

工具模块

  • 注册可用工具
  • 执行工具调用
  • 返回执行结果

记忆模块

  • 存储对话历史
  • 存储任务状态
  • 存储长期知识

输出模块

  • 格式化输出内容
  • 向用户展示结果
  • 记录交互日志

为何需要 Agent：LLM 单独无法完成的事情

1. 实时信息获取

LLM 的知识来源于训练数据，无法获取训练后发生的事情。Agent 通过搜索工具可以获取实时信息。

示例：

  • 用户：”今天北京的天气怎么样？”
  • Chatbot：”抱歉，我无法获取实时天气信息。”
  • Agent：调用天气 API → 返回实时天气数据

2. 精确计算

LLM 在复杂数学计算上容易出错。Agent 可以调用代码执行工具进行精确计算。

示例：

  • 用户：”计算 123456789 × 987654321”
  • Chatbot：可能给出错误结果
  • Agent：执行 Python 计算 → 返回精确结果

3. 多步骤任务

复杂任务需要多个步骤，LLM 单次输出难以完成。Agent 可以迭代执行多个步骤。

示例：

  • 用户：”帮我分析这份销售数据并写一份报告”
  • Chatbot：”请提供具体数据…”
  • Agent：
    1. 调用工具读取数据文件
    2. 执行数据分析代码
    3. 生成可视化图表
    4. 撰写分析报告

4. 外部系统交互

LLM 无法直接操作外部系统。Agent 可以通过 API 与各种系统交互。

示例：

  • 用户：”把会议安排到明天下午 3 点”
  • Chatbot：”我无法操作您的日历。”
  • Agent：调用日历 API → 创建会议 → 确认完成

5. 长期任务跟踪

跨会话的任务需要长期记忆。Agent 可以持久化存储任务状态。

示例：

  • 第一天：”帮我监控这个股票的价格变化”
  • Agent：记录任务 → 开始监控
  • 第二天：”股票价格怎么样了？”
  • Agent：从记忆加载任务 → 返回监控结果

LLM 选择考量

选择合适的 LLM 作为 Agent “大脑”时，需要考虑：

能力要求

  • 推理能力：复杂任务规划需要强推理
  • 工具调用：需要支持 Function Calling
  • 长上下文：长任务需要长上下文窗口
  • 输出格式：需要稳定遵循输出格式

成本考量

  • 调用成本：API 调用费用 vs 自托管成本
  • 延迟要求：实时响应 vs 批量处理
  • 并发需求：单用户 vs 多用户服务

可选方案

LLM 特点 适用场景
GPT-4/GPT-4o 强推理、Function Calling 复杂任务、企业应用
Claude 强推理、长上下文、安全 复杂分析、长文档处理
LLaMA 开源、可自托管 成本敏感、隐私要求高
Gemini 多模态、长上下文 图像+文本任务

总结

LLM 是 Agent 的核心组件，提供理解、推理、决策、生成能力。但 LLM 有明确的局限：无法获取实时信息、无法精确计算、无法维护长期状态、无法直接与外部系统交互。Agent 通过添加工具调用、记忆系统、规划机制，扩展了 LLM 的能力边界，使其能够完成更复杂的任务。

选择合适的 LLM 作为 Agent “大脑”，需要平衡能力、成本、延迟等多方面因素。

Agent 入门指南

什么是 Agent？

Agent（智能代理）是一种能够自主感知环境、做出决策并执行行动以实现特定目标的智能系统。在人工智能领域，Agent 代表了一种更高级的 AI 形态——它不仅仅是被动地响应输入，而是能够主动地规划、推理和行动。

Agent 的定义

从学术角度，Agent 可以定义为：一个能够感知环境并通过执行动作来影响环境的实体，其行为具有自主性、反应性、主动性和社交性等特征。

简单来说，Agent = LLM（大脑） + Planning（规划） + Memory（记忆） + Tools（工具）。这个公式揭示了现代 AI Agent 的核心组成。

Agent 与传统 AI 系统的区别

传统 AI 系统通常是单次交互的，例如：

  • 分类器：输入特征 → 输出类别
  • 推荐系统：输入用户历史 → 输出推荐列表
  • Chatbot：输入问题 → 输出回答

而 Agent 系统则具备多轮推理和行动的能力：

  • 可以分解复杂任务为多个步骤
  • 可以调用外部工具获取信息或执行操作
  • 可以根据中间结果调整策略
  • 可以维护长期记忆以支持上下文理解
特性 传统 AI Agent
交互模式 单次问答 多轮迭代
任务类型 简单/单一 复杂/多步骤
工具使用 无 主动调用
记忆能力 短期上下文 长期+短期+工作记忆
自主性 低 高

Agent 的三大核心能力

1. 感知（Perception）

感知是 Agent 获取环境信息的能力。Agent 需要通过各种方式感知其所处环境：

  • 文本感知：理解用户的自然语言输入
  • 视觉感知：处理图像、视频内容
  • 音频感知：理解语音、音乐等音频信息
  • 数据感知：从数据库、API、文件中获取结构化信息
  • 环境感知：了解系统状态、时间、资源等环境因素

感知的质量直接影响 Agent 的决策准确性。好的感知系统应该能够：

  • 准确提取关键信息
  • 过滤无关噪音
  • 处理模糊或不完整的输入

2. 决策（Decision Making）

决策是 Agent 的核心环节，涉及：

  • 理解目标：明确用户意图和任务要求
  • 规划行动：制定行动策略和步骤
  • 选择工具：决定使用哪些工具来完成任务
  • 评估风险：考虑行动的可能后果
  • 权衡选择：在多个选项中做出最优决策

现代 Agent 的决策主要依赖 LLM 的推理能力，但也需要配合：

  • 确定性规则（处理明确场景）
  • 搜索算法（探索可能的行动路径）
  • 优化方法（选择最优策略）

3. 执行（Action）

执行是将决策转化为实际行动的过程：

  • 工具调用：调用 API、执行代码、操作文件
  • 内容生成：撰写文本、生成代码、创作内容
  • 信息传递：向用户或其他 Agent 传递信息
  • 状态更新：更新记忆、记录进度
  • 结果反馈：将执行结果反馈给决策模块

执行过程需要：

  • 错误处理能力（处理失败情况）
  • 超时机制（避免无限等待）
  • 结果验证（确认行动效果）

Agent 的典型特征

自主性（Autonomy）

Agent 能够在没有人类直接干预的情况下运行。它可以：

  • 自主决定何时行动
  • 自主选择行动方式
  • 自主调整策略

自主性的程度可以分为：

  • 完全自主：Agent 独立完成所有决策和行动
  • 半自主：Agent 在关键节点请求人类确认
  • 监督自主：Agent 在人类监督下行动

反应性（Reactivity）

Agent 能够感知环境变化并及时响应：

  • 快速处理新的输入
  • 适应动态变化的环境
  • 处理突发情况

反应性要求 Agent 具备实时感知和快速决策的能力。

主动性（Proactivity）

Agent 不只是被动响应，还能主动行动：

  • 预测用户需求
  • 主动提供建议
  • 发现并解决问题

主动性是 Agent 区别于普通 Chatbot 的关键特征。

社交性（Social Ability）

Agent 能够与人类和其他 Agent 交互：

  • 解人类意图
  • 提供友好反馈
  • 与其他 Agent 协作或竞争

多 Agent 系统中，社交性尤为重要。

Agent 的应用场景

个人助手

  • 日程管理、会议安排
  • 信息检索、知识问答
  • 任务提醒、习惯养成

代码开发

  • 代码生成、补全
  • Bug 修复、重构建议
  • 代码审查、文档生成

数据分析

  • 数据清洗、预处理
  • 分析报告生成
  • 可视化创建

客户服务

  • 自动客服对话
  • 问题诊断与解决
  • 人工转接决策

自动研究

  • 文献检索与整理
  • 知识整合与推理
  • 报告自动生成

游戏与仿真

  • 游戏中的 NPC 行为
  • 战略决策与规划
  • 环境探索与交互

Agent 技术栈概览

构建 Agent 系统通常需要以下技术组件：

基础层

  • LLM：GPT、Claude、LLaMA 等大语言模型
  • Embedding：文本向量化模型
  • Vector Database：向量数据库（存储长期记忆）

框架层

  • LangChain：构建 LLM 应用的框架
  • AutoGen：微软的多 Agent 框架
  • CrewAI：角色扮演式的多 Agent 框架
  • Semantic Kernel：微软的企业级 Agent SDK

工具层

  • API 调用：与外部服务交互
  • 代码执行：运行 Python、Shell 等
  • 文件操作：读写文件、管理存储
  • 数据库：SQL 查询、数据管理

应用层

  • 对话管理：多轮对话状态管理
  • 任务规划：任务分解与调度
  • 结果展示：用户界面与反馈

总结

Agent 代表了 AI 系统的下一个发展阶段。它将 LLM 的强大语言能力与规划、记忆、工具调用相结合，形成能够自主完成复杂任务的智能系统。理解 Agent 的核心概念和特征，是深入学习 Agent 技术的基础。

OpenClaw 拆解

OpenClaw 拆解

OpenClaw 是一个面向 AI Agent 的架构概念，强调“开放工具调用”、灵活意图管理与多模态协作。本文从核心设计、工作流、模块拆解以及实践建议四个维度展开，帮助你快速理解 OpenClaw 的实现逻辑和应用场景。

1. 设计目标与价值

OpenClaw 的设计核心在于：

  • “Open”：开放工具、开放能力、可扩展的 Agent 架构。
  • “Claw”：像爪子一样抓取任务状态、抓取外部工具结果，并进行动态决策。

这意味着 OpenClaw 不仅是一套语言模型调用策略，更是一个“工具桥接层 + 意图引擎 + 执行器”的协作体系。

1.1 为什么需要 OpenClaw

传统 LLM 应用往往受限于单次“问答”式交互，缺乏对外部工具、系统状态和长期任务的有效管理。OpenClaw 通过以下方式解决该问题：

  • 将“工具调用”视为 Agent 的原生能力，而非后置插件。
  • 统一管理“意图生成、工具选择、结果验证、状态更新”四个环节。
  • 支持“跨任务协同”，例如：异步数据获取、独立工具链调度、上下文记忆缓存。

2. OpenClaw 核心模块拆解

OpenClaw 可以拆解为四个主要模块：

  1. 意图解析层（Intent Parser）
  2. 工具目录与能力层（Tool Catalog）
  3. 执行控制层（Execution Orchestrator）
  4. 反馈与校验层（Result Validator）

2.1 意图解析层

意图解析层负责把用户请求和上下文转化为可执行动作。这一层通常包括：

  • 请求分类：识别查询、命令、澄清问题等。
  • 目标分解：将复杂目标拆分为多个子任务。
  • 工具候选过滤：根据请求和权限，选定可用工具集合。

在具体实现中，它可以和“系统指令模板”、“元语义提示词”结合，生成更加稳定的 Agent 意图。

2.2 工具目录与能力层

OpenClaw 的“工具目录”是一组结构化声明，包含：

  • 工具名称
  • 工具输入规范
  • 预期输出类型
  • 失败策略
  • 权限与隔离边界

一个典型的 OpenClaw 工具目录既可以包含：

  • 内置能力（例如：文本摘要、分类、向量搜索）
  • 外部 API（例如：搜索引擎、数据库、CI/CD、设备控制）
  • 复合工具（由多个基础工具组成的工作流）

2.3 执行控制层

执行控制层是 OpenClaw 的“爪子”，负责在 Agent、工具与环境之间传递状态。它的职责包括：

  • 动态调度工具调用
  • 控制并发与顺序策略
  • 管理重试与异常回滚
  • 维护工单上下文和执行日志

这一层通常需要与“中间缓存”和“流水线节点”结合，才能保证复杂任务下的稳定性。

2.4 反馈与校验层

智能 Agent 的价值不在于“调用工具”，而在于“工具调用之后是否得到可信结果”。

OpenClaw 的反馈与校验层主要负责：

  • 工具输出一致性检查
  • 结果可信度打分
  • 运行状态回传给意图层
  • 出错时生成补救指令或澄清问题

例如，当工具返回“模糊结果”时，OpenClaw 可以引导 Agent 生成“补充问题”或“重新调用另一个工具”。

3. OpenClaw 工作流示例

下面是一个典型的 OpenClaw 工作流：

  1. 用户发起请求：”帮我查一下最新的模型微调费用。”
  2. 意图解析层识别为“信息检索 + 费用估算”任务。
  3. 工具目录筛选“搜索引擎工具”和“价格计算器工具”。
  4. 执行控制层先调用“搜索引擎工具”，获取最新价格说明。
  5. 结果校验层检查返回内容是否包含定价信息。
  6. 如果结果可信，则再次调用“价格计算器工具”进行汇总。
  7. 最终将结构化答案返回给用户，并写入会话记忆。

这个流程中，OpenClaw 的优势在于：

  • 清晰的“工具边界”
  • 结果检查后的“可控执行”
  • 可扩展的“补救与澄清”机制

4. OpenClaw 的实践建议

4.1 明确工具能力边界

在构建 OpenClaw 时，必须把每个工具的输入、输出、失败行为写清楚。这样才能避免 Agent 误用工具、或在失败时出现“语义级错误”。

4.2 保障可观测性

在执行控制层中记录每一次工具调用、参数与返回值，是调试 OpenClaw 的关键。可观测性可以帮助你：

  • 发现“工具误用”
  • 定位“意图解析失败”的根因
  • 监控执行性能与失败率

4.3 保持“回退与澄清”能力

当外部工具数据不可用或结果不可信时，OpenClaw 不应直接给出错误结论。应优先采用：

  • 自动重试
  • 备用工具降级
  • 向用户澄清

4.4 与业务流程结合

OpenClaw 最适合的场景是：

  • 多工具、跨系统协作的任务
  • 需要上下文管理与多步推理的业务流程
  • 需在工具调用前后进行结果校验的智能服务

在这些场景中，OpenClaw 可以把“LLM 推理”变成“可审计、可扩展的业务执行引擎”。

5. 结语

OpenClaw 不是单纯的模型方案，而是一套“Agent 架构思路”。它关注的是：

  • 如何把工具调用设计成 Agent 的基础能力；
  • 如何在多步任务中保持执行一致性；
  • 如何让结果校验成为流程中的一部分。

通过这一层拆解，我们可以更清晰地看到 OpenClaw 的价值：它将 LLM 从“智能问答”升级为“可控执行、可扩展工具协作”的平台级能力。

关键点：OpenClaw 的核心在于“开放工具调用 + 动态执行控制 + 结果校验”，而不是简单地把外部 API 接入模型。
